# 大文件场景的 GUI 边界审查

日期：2026-10-09（Asia/Shanghai）。初始 GUI SHA256：`0d59d53e067da326984702ece5939347448a829012b564363eb9469c42b25f87`。初次复核不重复处理真实大文件、不修改 GUI；只使用自建透明 Tk 窗口、微小合成工作簿和受控故障注入。随后按授权实施下述局部修复。

结论：正常长任务的线程边界、文件内 MemoryError 的批次恢复没有发现新缺陷；**确认并修复一个线程创建阶段 MemoryError 会让窗口停在运行态的 P2 异常分支缺口**。这项结论来自明确的故障注入，不能表述为真实大工作簿已经触发该故障。

证据：[probe_gui.py](probe_gui.py)、[gui-probe-results.json](gui-probe-results.json)。执行前后 GUI 哈希相同。

## 已确认并修复：GUI-MEM-01（P2）

定位：`excel_unmerge_gui.py:247` 起的 `launch_batch`；第 268 行 `threading.Thread(...)` 在 try 之外，第 273 行只捕获 `RuntimeError`。

触发条件：GUI 已设置 `running=True` 并禁用操作按钮之后，线程构造或 `worker.start()` 因分配资源抛出 `MemoryError`。分别在这两个位置注入一次 MemoryError，均产生相同结果：

- 异常进入 Tk 回调错误处理，后台线程没有开始处理；无输出文件。
- `running` 保持 True，队列为空，没有任何代码再发送 done。
- 开始、重试、继续都保持禁用；即使直接调用恢复方法也因 running 守卫退出。
- 点关闭只设置停止请求并继续等待，没有 worker 能结束等待，窗口无法通过正常关闭动作退出。

这是状态恢复缺口，不是数据覆盖问题。真实系统内存不足时是否具体落在这个分配位置未实测，不能推断发生率。修复把线程构造和启动一并纳入启动失败处理，对 `MemoryError` 与现有 `RuntimeError` 统一恢复到待处理状态并保留中文内存提示，使继续处理和关闭重新可用。只捕获这两个确定异常，不改变当前文件不可中断的保存契约。

修复后 GUI SHA256：`b89ec395e909837c8915a878afc0fba48f2900979d78f693661d87fa368a5aec`。新增两个真实 Tk 回归分别注入构造、启动阶段 MemoryError；修复前均捕获到未处理的 Tk 回调异常，修复后验证无回调异常、恢复空闲、原文件不变、无输出/假完成、保留未处理项、可继续成功、新批次可正常开始，以及实际关闭窗口。

证据：[gui-memory-recovery-before.txt](gui-memory-recovery-before.txt) 为 2 项预期失败；[gui-memory-recovery-after.txt](gui-memory-recovery-after.txt) 为已有 GUI/worker 测试与新增回归合计 **15/15 通过**。原始故障探针 JSON 保留不覆盖；最终全套引擎/打包验证由主验收继续执行。

## 已通过的受控场景

1. **持续占用 Python 解释器时 GUI 仍能处理事件。** worker 执行 2 秒有界纯 Python 运算，再真实处理一个微小工作簿。20 ms 主线程心跳得到 70 个样本，中位间隔 26.37 ms、最大 60.33 ms；未出现 Tk 回调异常。200 ms 定时的停止请求于 0.247 秒实际执行，350 ms 定时的关闭请求于 0.424 秒执行；窗口继续存在。当前文件于 2.014 秒完成保存，后一个文件没有开始，保留为待处理。
2. **文件处理阶段 MemoryError 可恢复。** 第一项由 `process_file` 抛 MemoryError，第二项真实处理成功；界面显示内存提示，最新状态为失败 1、成功 1。去掉故障后仅重试失败项，最终成功 2；之前成功项没有生成 `_2`，无 Tk 回调异常。

CPU 探针没有分配大块内存，不等于数 GB 工作簿的响应 SLA。长时间持有 GIL 的 C 调用、垃圾回收、系统换页或操作系统终止进程不在此实测覆盖内；不能因一个 worker 线程或一次注入成功就承诺全局内存耗尽时 UI 必定可用。

## 产品体验与现有契约

- “当前文件完成后停止”和运行中关闭窗口都只阻止后续文件。单文件处理几十秒时，停止后继续等待该文件完成符合当前契约；不建议本轮直接杀线程或截断写入。
- 进度条按已完成文件数计数。单个大文件期间可能长时间停在 0/1，但当前文件名、停止请求提示仍正确；这属于缺少文件内部进度的体验限制，不能报作计算卡死或取消失效。
- 后续可考虑显示已用时、当前阶段或单文件活动指示。没有可靠总工作量时不应虚构百分比；此建议不作为本轮新增范围。
