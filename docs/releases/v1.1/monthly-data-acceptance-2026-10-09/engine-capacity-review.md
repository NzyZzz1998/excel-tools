源文件 104,185,338 字节（99.36 MiB），SHA-256 `0849fd0df036c0dc6e18b7a9f54ba5e0d9a512e9cb3d30beb3acacb382f4c6e8`。引擎 SHA-256 `1d761a9f897b545c367514069e755f1aa270f1d9a777d963ffe1af41b606b5eb`。

结论：该文件进入逐行流式路径；未发现本次形态会重新触发整表 DOM 或共享字符串整体载入的路径，也未发现需要预先拒绝的内容。主要成本是约 1364 万原格的解析、约 1667 万结果格的序列化，以及磁盘临时文件；不能把此前日表的 72 MiB/约 1 分钟直接推广到月表。实际是否通过及耗时/RSS应以 EXE 运行和独立内容校验报告为准。

## 行索引与合并复杂度

主表实际范围 `A1:V757636`，757,636 行、22 列、13,638,731 个实体格；次表 `A1:B1`，1 行、2 格。源文件两表的 dimension 都是 A1，但主表转换会扩展到实际范围；无合并的次表按原样保留，不能把保留其错误 dimension 当作数据丢失。

- `RowSpoolBuilder.rows`（343-388 行）只保存每行的编号、磁盘偏移和字节长度；单元格 DOM 在行结束时释放。重放时增加行号集合和排序列表（441-447 行），没有按 1364 万格创建全局索引。内存随约 76 万行增长，不是严格常数内存。
- 在本机 64 位 Python 上，用 10,000 行合成索引测得相同基础容器/对象拓扑约 230 字节/行，按行数粗估约 166 MiB；字典扩容、整数大小、解析器和分配器会改变实际峰值，此数不是应用 RSS 预测或限制。相比日表行数约 4 倍，月表行索引明显更大，应检查实测峰值。
- 本表 1,279 个纵向合并、1 个横向合并，无矩形合并；独立盘点最大同时活动合并数为 4，最大区域高度 31,925 行。重叠检测按开始行排序和活动区间扫描（61-78 行），当前形态不会形成每个区域扫描所有 1,280 个区域的成本。重放时每行只遍历活动合并，并检查现有最多 22 列（445-528 行）；本文件没有大量同一行活动区域的复杂度风险。
- 纵向范围加入行号集合的工作量约等于各范围高度之和，约 303 万次，仍需 CPU，但不累计数百万独立目标单元格 DOM。范围内各行已存在，没有从很少输入行扩成百万新行的形态。
- 默认模式预计拆分 1,279 个区域，填充 3,029,255 个单元格，保留 1 个横向合并。原格均有内容、目标不存在隐藏独立内容，预计主表结果实体格 16,667,986 个，增加约 22.2%。新增值均为 inlineStr；不能用格数增长百分比直接推算字节数或压缩后文件大小。
- 独立盘点没有公式、vm/cm/extLst、隐藏内容冲突、相交合并、乱序/重复/缺坐标。默认/全部模式只差拆掉一处横向表头并增加 6 格；本轮不重复整本全部模式验收，因此不声称本月表全部模式已实跑。

## 临时磁盘与边界

主表转换同时使用原行 spool、结果行 spool 和最终转换 XML 临时文件（415、550-570 行）；在最终 XML 拼装末期，空间约为“序列化原行大小 + 2 × 序列化结果 XML 大小”，而不是 99 MiB 压缩文件大小。其后两份内部 spool 关闭，转换 XML 保留到 ZIP 结果写完。这里主表原 XML 已约 699 MiB，临时盘应按数 GiB 量级预留，并以实际输出/监控为准；本轮检查时系统临时盘所在 C: 与结果所在 E: 都有超过 1 TiB 可用空间，无当前磁盘容量阻断。

输入中的大块行外元数据会留在文档骨架，极大单行和大量活动锚点也会增加内存；本次实际表窄、行外结构少、活动区域最多 4，并未呈现这些边界。代码没有全局资源预算，未来更宽、更长文本、更多工作表的文件仍应单独测量，不能从此样本保证任意 100 MiB 工作簿的容量。

## 预备 Excel 客户端验收器

`validate_excel_chunked.ps1` 已准备默认模式校验，但本次审查没有启动 Excel。脚本独立流式读取源合并地址，并从源 Excel Value2 当前块取得锚点；每 5,000 行读取源/结果两个值数组，直接逐格比较，不另建完整预期数组，不把业务值写入报告。主表将比较完整 16,667,992 格矩形（含普通空白），次表比较 2 格，避免仅比较实体格漏掉意外填充。

比较器无 Excel 自测通过 60,012 格跨块填充，并验证普通空白/空格、值 0、保留横向合并、标量和故意错值/误填的失败路径。自测不是 Excel 客户端实跑。脚本开新 Excel 实例并确认 PID 不在预存进程集合，禁宏/外链，只读开两本，失败同样在 finally 中逐项关闭且不保存；清理异常会令 passed 为 false，源/输出 SHA-256 前后必须相同，实例退出也属于通过条件。

Excel 自身仍同时打开两本，其内存不受 5,000 行块大小约束；建议由主验收外层仅监控自建进程树，按 8 GiB 与当时可用内存三分之一中的较低值、15 分钟设置保护。若保护触发，应记录为验收器主动终止，不能称为应用 OOM 或内容校验失败。报告不包含原值、公式文本或商品/供应商数据，仅地址、统计、身份哈希和异常类型。

## 外层保护交接

已补标准库监控器 `monitor_excel_validation.py`。实际实现进一步缩小终止范围，只监控并可终止一个经 COM HWND 确认的新 Excel PID，不自动终止其进程树、用户已有 Excel 或 PowerShell。脚本通过可选 `-Progress` 原子写入 run nonce、PowerShell PID/精确创建 FILETIME、Excel PID/精确创建 FILETIME 和阶段；确认拥有新实例后立即写入，开源/结果前刷新，随后约每 5 块刷新计数。

监控器核对 nonce、生产者身份、Excel 创建时间、EXCEL.EXE 文件名并保留该原始进程句柄，避免 PID 复用重定向终止。每约 100 ms 采样，限额为启动时可用物理内存三分之一与 8 GiB 的较低值，整次验证期限 900 秒。资源超限仅终止已确认 Excel，给 PowerShell 60 秒进入 finally 并写失败报告；若未获得确认身份或清理仍卡住，则记录待人工检查，不猜测并终止其他进程。监控主动停止时整体 passed 必为 false，并明确是验收保护介入，不是产品崩溃。

无 Excel 自测验证了旧 nonce、错误 PID/创建时间、旧进程、错误可执行文件拒绝，使用 fake 对象验证确认后终止分支，并读取当前 Python 进程句柄和内存验证 Windows API 接口。没有启动 Excel 或终止真实进程；PowerShell 比较器自测也重复通过。正式客户端执行交由主验收安排。
