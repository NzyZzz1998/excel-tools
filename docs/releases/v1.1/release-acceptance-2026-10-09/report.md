## 数据量与性能边界

用户先表示不确定月度行列数，随后纠正实际单日约 5 万行。已做实验取的是“每日缺货Top50 (1).xlsx”首表 402 行，按行重复 1/7/31 倍，第二张筛选说明表保持原样；表头和汇总也随之重复，只用于小报表结构的负载测试。主代理此前将其称为日明细并推算月度规模，选样判断不成立，已更正并暂停发布。v1.0.0 基线直接取 Git tag，身份核对见 [baseline-identity.json](package/baseline-identity.json)。

数据来源：[初始基线](performance-initial.json)、[最终引擎](performance-final.json)、[复现脚本](performance_benchmark.py)。本机 Python 3.12.8，单次、同输入、独立子进程样本；处理时间仅 `process_file`，不含 EXE 启动、选文件、Excel 打开。RSS／专用内存每 10ms 采样，可能错过瞬时峰值；两种内存口径不能相加。31 倍样本专用内存峰值 1111.68 MiB，工作集约 1.02 GiB，压缩文件仅约 2.29 MB，说明压缩体积不足以估算内存。

缓冲修复将 31 倍的候选工作集从 1159.39 降至 1042.21 MiB，仍比 v1.0.0 高；没有宣称内存全面优于旧版。内容校验覆盖 336263 个输出实体格及保留合并、非目标部件、源 SHA；没有把业务汇总当作可重复相加的月度口径。

较大文件确实可能变慢或内存不足。当前完整 DOM 会随工作表展开占用内存，不能按这个样本外推 10 万／100 万行容量；也没有在低内存机器上验证。业务允许时按日期分成独立文件逐批处理，保留原文件。更大规模若成为正式要求，下一阶段应设计流式读写并用真实月报验证，不能只改缓冲就宣布解决。

**50,250 行压力补测未完成处理。** 用户纠正后，将同一 Top50 结构扩为 125 倍、27 列，压缩后 9,201,657 字节。工作进程运行约 19.111 秒时采样工作集达到 3073.38 MiB，超过探针事先设置的 3 GiB 限额，由探针主动终止；原文件 SHA 不变。[原始记录](performance-stress-50k.json)。这证明当前结构下资源压力显著，不能认定已满足约 5 万行日明细验收；不把人为限额写成真实 OOM、应用自身崩溃或最大容量。未产出经核对的结果，不能填写成功耗时。真实日明细形态仍未知，因此继续等待文件定位，不外推真实表的准确内存与速度。

此前 9 个已计时输出经验证脚本补强后重新核对，1,269,153 次实体格比对及独立精确坐标集合全部通过，计时证据未改：[复核记录](post-audit-validation.json)、[独立审查](performance-review.md)。文件系统成功分支补齐实际 SHA 断言后 [四项复验](filesystem-results-final-audit.json) 通过。
