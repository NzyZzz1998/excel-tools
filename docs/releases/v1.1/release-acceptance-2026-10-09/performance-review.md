# 性能与文件系统证据独立复核

现有记录的单位、计时及输出内容结论成立，但**不能据此判断真实日明细或月度文件的性能**。用户已明确实际单日明细约 5 万行；本次取样是 Top50 报表的 402 行首表。31 倍仅为 12,462 行、27 列的同结构重复负载，不应称为月度规模。

## 数字与对照

31 倍样本的引擎处理壁钟为：v1.0 `8.4116 s`；调整前 v1.1 `7.2278 s`；当前 v1.1 `7.4538 s`。当前子进程从启动到退出为 `7.5478 s`，与处理函数计时是两个指标，都不是打包 EXE/GUI 的完整交互耗时。

内存按 `1024²` 换算为 MiB。当前采样 RSS 峰值 `1042.21 MiB`，private 峰值 `1111.68 MiB`；两者分别取峰值，不能相加。RSS 比调整前 v1.1 的 `1159.39 MiB` 低约 `10.11%`，仍比 v1.0 的 `936.45 MiB` 高约 `11.29%`。当前耗时比本次 v1.0 测量低约 `11.39%`、比调整前 v1.1 高约 `3.13%`。

这些都是单次、顺序执行的本机样本，未做重复测量、统计区间或缓存顺序随机化。当前版本同时包含内容修复和 StringIO 调整，因此不能把全部差异单独归因于 StringIO。初始与最终同倍数输入已核对为逐字节一致，基线和候选引擎 SHA256 也已记录。

## 校验补强与复验

发现原 `verify()` 以行号取模后核对模板、数量及排序，却未约束实际行范围。极小合成反例把唯一的 A1 移到 A2，原函数仍返回成功。现在在取模前断言 `1 <= row <= span * repeat`，该反例已被拒绝。此处是验收器缺口；未发现现有引擎输出发生这种错误。

`post_audit_validate.py` 对 6 个初始、3 个最终已生成输出重新验证：共 `1,269,153` 次物理单元格内容比对，另独立检查精确地址集合及重复格，全部通过。31 倍每个输出的 `336,263` 格内容断言成立。检查还包含保留合并、格顺序、格属性/子树和非目标 ZIP 部件；本脚本不覆盖修改工作表的全部非单元格属性或 Excel 视觉表现，相关原业务验收另行保留。

文件系统脚本在目录碰撞成功分支原来只写出 `source_preserved=true`，没有当场断言源 SHA。已补断言，并重新以 `final-audit` 执行四项真实 Windows 探针：并发结果唯一且旧结果/源不变、同名目录跳过、只读源、独占锁拒绝及解锁重试，全部通过。原 `filesystem-results-final.json` 保留不覆盖。

证据见 `post-audit-validation.json`、`filesystem-results-final-audit.json`。初始及最终性能计时 JSON 的 SHA 已核对未变；没有重跑或替换计时。引擎保持冻结，SHA256 为 `877485d3c497df2cdf83fe1a7729002ef0b91c1e964109cc2f684fc068227f75`。

## 必须保留的边界

- 10 ms 轮询得到的是采样进程内存峰值，可能漏过瞬时峰值，也不包含监测父进程、Excel 或 GUI 的内存。
- 3 GiB RSS / 120 s 是探针的终止条件，不是应用自身的限制或保护。若后续 125 倍、50,250 行同结构模拟被探针终止，应报告触发的资源阈值，不能称为应用真实 OOM。
- 重复同一报表保留了相同值分布、样式表、共享字符串及合并形态，无法代表真实明细中的不同列数、字符串、公式、格式、图片和工作表数量。应等待用户指定真实日明细后再决定适用规模；当前不据此批准性能验收或发布。
