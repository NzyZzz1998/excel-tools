验证日期：2026-10-09（Asia/Shanghai）。代码基线：`96cfbfe`。

结论：本轮未发现需要阻止 v1.1 发布的 GUI 数据安全、停止、恢复或错误处理缺陷。新增 7 项真实 Tk 状态边界探针全部通过，无 Tk 回调异常。另确认一个可后续优化的 P3 极长文件名布局限制。

## 验证方式

使用已有 Python 3.12.8 / openpyxl 3.1.5 环境；只创建本探针自己的透明 Tk 窗口和临时合成工作簿。没有操作用户窗口、读取业务工作簿、修改应用代码或发布。探针结束后临时文件清理。

入口：[probe_gui_boundaries.py](probe_gui_boundaries.py)。运行证据：[gui-boundaries.txt](gui-boundaries.txt)。应用 GUI SHA256：`0d59d53e067da326984702ece5939347448a829012b564363eb9469c42b25f87`，执行前后相同。

| 状态边界 | 结果 |
|---|---|
| 工作线程启动报 RuntimeError 后再继续 | 文件仍为待处理，完成/成功/失败均为 0；错误详情保留；恢复后实际处理成功 |
| 初始两项失败、两项未处理，重试与继续分别中途停止后交替恢复 | 失败集与待处理集互不混淆；最终四项各生成一次输出，无 `_2` 重复结果 |

## 非阻断观察 GUI-LAYOUT-01（P3）

触发条件：窗口缩到 680×540，正在处理的真实合成工作簿文件名为 250 字符（245 个中文字加 `.xlsx`）。为稳定观察，只在 worker 中用 Event 暂缓实际处理，之后释放并由实际引擎完成。

现象：运行状态标签自动换行后高 106 像素，下面结果区域被 pack 压到不可见。停止按钮仍可见；任务正常成功保存；完成汇总变短后结果区自动恢复。没有日志丢失、输出损坏、恢复失败或永久控件不可用。

定位：`excel_unmerge_gui.py` 的 `status_label.pack(fill="x")` 与紧随其后的 `result_frame.pack(fill="both", expand=True)`。极长状态文本获得所需高度，留给结果区的高度为零。

建议：后续版本可限制运行状态显示行数或对文件名做中间省略，在结果日志保留全路径。现有最小尺寸和接近文件名上限的组合下可临时放大窗口查看；本项不要求当前发布前改动。此结论仅覆盖所述环境与触发条件，不把未测的 DPI/其他窗口尺寸记为通过。

## v1.1 EXE 启动耗时观察

对 SHA256 为 `066ca4a1c7fe7fd2ac80a06ddc3969dbd178f5181983d8767d2c219078485d5c` 的已验收 EXE 连续启动三次，从创建进程前计时，到自己的窗口、26 个原生子控件齐备且 WM_NULL 消息成功响应，分别为 **1.062、1.104、1.017 秒**，中位数 **1.062 秒**。窗口首次可枚举为 0.983～1.074 秒。

入口：[measure_startup.py](measure_startup.py)。详细证据：[startup-timing.json](startup-timing.json)。启动使用 SW_HIDE；为让 Tk 实际完成布局，随后只把属于本次 launcher 子进程树且 EXE 路径一致的窗口映射为完全透明、离屏、非激活状态。没有键鼠输入；三次均通过自己的 WM_CLOSE 正常退出 0，无强制结束或残留进程。

这只是本机 Windows 11 的顺序启动观察。没有重启或清理操作系统缓存，预先核对 EXE 哈希也会预热文件缓存，故首轮不能称为真正冷启动；三次差异不能作为冷暖启动保障。未找到项目内可直接使用的 v1.0 EXE/包，没有下载或测量旧版，不能推断 v1.0 性能。此项没有处理工作簿或打开 Excel，只用于把程序启动与引擎处理、Excel 客户端打开分开记录。

观测器校准说明：初版探针持续保持窗口隐藏，在 26 控件条件上超时；后续校准观测显示离屏映射前为 20 个原生子控件，采用上述离屏非激活映射后稳定观察到 26 个。该探针超时不计为应用启动耗时。
