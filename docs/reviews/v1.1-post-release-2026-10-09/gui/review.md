# v1.1 发布后 GUI 与交付体验复核

日期：2026-10-09。只读审查已发布 v1.1，GUI SHA256 `d3a1c273f0d4bb333d26945b8b39061daa064824e413601e711aeb9ab8d2c4c0`。本轮没有发现新的数据丢失、线程恢复或安全保存功能缺陷；以下四项是有证据的体验改进候选，优先级不表示已发布包违反既有合同。

没有枚举、操作或关闭用户正在运行的 EXE 实例。新增探针只建立本进程 PID 42408 的 withdrawn Tk 窗口和临时合成工作簿；文件对话框与打开 Explorer 的调用均被替代，未发送真实键鼠输入。两项观察完成、无 Tk 回调异常，合成文件清理，应用源码哈希未变：[探针](probe_ux_states.py)、[结果](probe-results.json)。

## 1. P2 优化：长文件没有已用时或文件内活动提示

**定位：** `excel_unmerge_gui.py:89–97` 每文件只发送开始、结果和结束事件；`:265–266` 将本轮进度置零；`:290–295` 设置当前文件文案；`:313–315` 只有整个文件返回后才推进进度。

**事实与证据：** 已发布 EXE 处理真实月表耗时 405.875 秒，期间截图显示“本轮第 1/1 个，已处理 0 个”和静止的文件进度条，程序最终成功。窗口没有已用时或文件内部阶段：[处理中截图](../../../releases/v1.1/monthly-data-acceptance-2026-10-09/exe/processing.png)、[执行与内存记录](../../../releases/v1.1/monthly-data-acceptance-2026-10-09/exe/execution.json)。停止按钮明确表示“当前文件完成后停止”，源码 `:278–282、353–358` 及 PRD 也规定文件边界安全停止；等待当前文件完成不是取消失效或合同违约。

**影响（推断）：** 数分钟保持相同画面时，用户难区分仍在处理和停滞，可能重复启动程序或强制结束进程。此处没有证据证明当前程序卡死，也没有证据证明用户已经做过这些操作。

**最小改进：** 增加每文件已用时，并将现有数值明确标为“已完成文件数”；处理中可增加无百分比的活动动画及“停止将在当前文件安全完成后生效”。动画只表示正在等待任务，不能宣称引擎一定正常推进。若以后引擎能提供真实阶段，再显示读取/转换/保存；不要依据耗时伪造百分比或剩余时间。

**验证：** 用受控延迟的合成文件检查已用时持续更新、文件计数不提前增加；请求停止后仍安全完成当前文件，仅后续项保持待处理。无需为这一界面改动重跑整份月表。

## 2. P2 优化：新文件选择与上次任务恢复共用界面，操作目标容易混淆

**定位：** `excel_unmerge_gui.py:194–202` 只更新下一次开始所用的 `files`、文件列表和“已选择”文案；`:214–227` 的重试/继续仍读取旧 `file_states`；`:254–255` 恢复旧选项快照，但不把文件列表改成恢复对象；`:304–305` 按旧任务设置恢复按钮。

**事实与证据：** 合成 A 首次失败、修复后选择 B，界面显示 B 和“已选择 1 个文件”，重试按钮仍可用。点击“仅重试失败项”实际只处理 A，顶部仍显示 B，最终汇总成功 1/1；A 有输出，B 没有输出。日志确实保留 A 的完整路径，没有数据丢失：[probe-results.json 的 recovery_selection](probe-results.json)。这符合 [PRD](../../../releases/v1.1/prd_v1.1.md) 的“选择新文件不开始新任务，旧任务仍可恢复”，并非把旧状态当成新缺陷重新报告。

**影响（推断）：** 用户可能把成功 1/1 归到顶部所选的 B，尤其两个目录存在同名报表时。程序实际处理集合正确，界面对“下一次选择”和“上次恢复任务”的说明不足。

**最小改进：** 恢复按钮明确命名为“重试上次失败项（N）”“继续上次未处理项（N）”；选择新文件后同时提示上次任务仍可恢复，并标明其目标。保留旧任务，不直接清空失败/待处理集合；恢复过程中应显示实际处理对象，而非仅保留下一批选择列表。

**验证：** A 失败或暂停后选择 B，检查用户可在执行前辨认恢复仍指向 A；恢复只处理 A，点击“开始处理”才建立 B 的新任务。覆盖不同目录同名文件，确保列表、文案和实际运行集合一致。

## 3. P3 优化：跨目录批次的单一结果按钮只定位最后一个目录

**定位：** `excel_unmerge_gui.py:153–155` 按钮名为“打开结果目录”；`:323` 每次成功覆盖单个 `output_directory`；`:339–346` 仅打开该目录；`:332` 其余结果路径只有文本记录。

**事实与证据：** 在两个目录各放一份同名合成输入，处理后两份输出均存在、汇总成功 2；调用结果按钮只打开第二个目录，日志包含两条完整输出路径：[probe-results.json 的 multiple_directories](probe-results.json)。“结果另存到原文件目录”已有明确说明（`:145–146`），结果没有丢失。

**影响（推断）：** 批量交付时，用户从该按钮进入一个目录后可能漏找其他目录的结果；同名输出在 Explorer 中也不足以说明来自哪份输入。

**最小改进：** 先将按钮改为“打开最近结果目录”，使名称与行为一致；给结果日志中的各输出增加“定位”或“复制本批结果路径”入口，使用本任务已有路径即可，不要求加入持久任务历史或修改另存规则。

**验证：** 两目录同名输入均成功后，每份结果都能独立定位，目录标题或复制结果包含完整路径；失败重试不移除此前成功路径，普通新任务仍按既有合同重置。

## 4. P2 优化：同为 v1.1 的验收副本缺少可见的构建与运行位置标识

**定位：** `excel_unmerge_gui.py:24–25、116` 标题仅由固定应用名和版本号组成。

**事实与证据：** 只读核验本地两份已有 EXE，SHA 分别为旧候选 `066ca4a1…` 和已发布 `239b1456…`；已有窗口记录均为“Excel 数据处理工具 v1.1”，两份 Windows 文件属性的 FileVersion/ProductVersion 均为空：[version-copies.json](version-copies.json)。旧候选 [构建清单](../../../releases/v1.1/business-acceptance-2026-10-09/fixed-build/verification-manifest.json) 与本次 [已发布身份](../../../releases/v1.1/monthly-data-acceptance-2026-10-09/candidate-identity.json) 分属不同产物。没有启动这些 EXE，也没有识别用户当前运行的是哪份，不能据此断言用户误用了旧包。

**影响（推断）：** 当用户直接从验收目录启动或反馈截图时，单看 v1.1 无法确认是否为包含最终修复的包，容易在定位性能或恢复问题时使用错误基线。

**最小改进：** 交付时提供固定的已发布版本入口；后续加入轻量“关于/复制诊断”信息，包含版本、构建短标识和当前 EXE 路径，并写入 Windows 文件版本属性。不必在主窗口显示长 SHA，也不移动或关闭正在使用的旧副本。

**验证：** 两个同为 v1.1 的测试构建能通过复制诊断明确区分，记录与打包清单一致；从不同解压目录运行时路径反映实际入口，截图或诊断不会混淆旧候选与正式包。
