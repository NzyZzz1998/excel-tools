# v1.1 发布后性能只读复核

日期：2026-10-09。结论：当前可确认的 CPU 热点是逐行重复解析/序列化；本轮微优化只有约 0–3% 的合成差异，不足以支持立即合入，也不能宣称真实月表约 6 分 46 秒能明显缩短。产品层应先改善长任务反馈。若继续投入引擎性能，建议仅保留下面两个有边界的研究方向。

本轮没有读取真实工作簿内容、没有运行 104 MB 月表、没有启动或操作 Excel/产品窗口、没有修改应用或标准库。源码基线 HEAD 为 `4e013c4ded2af26c6546fa16a1860fff282e5842`，与应用提交 `067834455de167d86351b5ab338c518744ec4afa` 的 engine/gui 内容无差异。引擎 SHA-256 为 `1d761a9f897b545c367514069e755f1aa270f1d9a777d963ffe1af41b606b5eb`。本地只有 v1.0.0 tag，未为本审查抓取/创建 v1.1 tag；应用身份通过实际提交和文件哈希核对。

## 证据方法与限制

合成样本为 4,000 行、22 列、72,016 个原实体格，16 个纵向合并，最多 4 个同时活动，每段 1,000 行；预计填充 15,984 格，输出 88,000 个实体格。普通列使用 3 列合成 inlineStr、15 列数字，锚点也是明确合成文本。结构参考已知月表的窄行/活动合并数量，未复制业务值，也不模拟真实文本长度、磁盘缓存或 ZIP 压缩行为。

通过公开的 `transform_sheet_stream` 对内存中的合成 XML 和磁盘 TemporaryFile 运行，计时包含两遍变换与临时文件操作，不包含构造 fixture、输出哈希、ZIP 解压/压缩。独立加载的实验模块只替换自己的函数，没有修改产品文件或全局 minidom 实现。

- `baseline.json`：1,000 行预热、3 次无 profiler 基线中位 **1.728 秒**；同输入 cProfile 为 **7.083 秒**，约 4.10 倍扰动。剖析只用来定位调用与相对成本，不能把 profiler 秒数外推到用户月表。
- `candidate-results.json`：5 种实现按位置轮换，各 5 次，无 profiler。基线中位 **1.727 秒**，单次范围约 1.724–1.784 秒，说明小差异需要谨慎看待。
- `path-results.json`：后续有界路径对照，各 5 次，无 profiler；匹配基线中位 **1.729 秒**。没有进一步扩大全量跑数。
- 所有已计时变体都核对拆分/填充计数和输出 SHA-256 与基线完全一致。50 + 20 项小样本等价检查覆盖 CR/LF/TAB 实体、CDATA/PI、前缀遮蔽、继承 xml:space、非规范地址、横向保留/矩形、无匹配，以及公式/隐藏元数据拒绝；这些检查不是完整生产保真证明。

## 建议一：只对重复行序列化做下一轮独立实验，暂不重构发布版

证据与定位：

- `excel_unmerge_fill.py:386` 首遍对每行序列化后落盘，`468` 将活动行重新解析为 DOM，`529` 再次序列化。
- 4,000 行样本中，`serialize_xml`（158 行）调用 **8,003 次**，cProfile 累计 **2.299 秒**，约变换剖析时间的 32.5%；逐行 `minidom.parseString` 调用 **4,000 次**、累计 **1.306 秒**。这些累计时间与上层 parseFile/store_row 有包含关系，不能相加当作独立占比。
- 只对已知合成 XML 提前建立“原行 bytes”映射，替代首遍 `serialize_xml(node)` 的反事实实验，中位 **1.729 → 1.566 秒（约 9.45%）**。它排除了通用原行提取/索引的成本，只是潜在收益上界线索；该内存映射不适合大表，绝不能直接移入应用。

最小研究切口：保持逐行落盘与现有第二遍保真逻辑，仅研究能否利用首次解析的字节区间，将 UTF-8 原始行直接落盘/索引，从而省掉一次完整行序列化。不要同时更换 Excel 库或引入并行框架。若可行，应继续使用磁盘 spool 和 O(rows) 索引，不能把所有原行 bytes 常驻内存。

风险：原始片段不能丢失 namespace/xml:space 上下文；UTF-16、文档类型/实体、自闭合行、带空白的关闭标签及块边界需要明确处理。当前首遍序列化已经替这些边界做了规范化，绕过它并非无风险。最稳妥的研究方式是限制并验证可用快路径，其余回退到现有序列化；任一语义差异都应回退。下一步验收应先跑现有 95 项、流式差分、前缀/实体/空白回归，再经用户允许实跑真实日/月文件的全量 oracle 和 Excel 核验。不能用上界实验承诺月表提速百分比。

## 建议二：仅把无匹配预检作为场景性备选，避免拖慢常规处理

证据与定位：`transform_sheet_stream` 在 `418` 完成整表 DOM 行构造、检查、序列化并落盘后，才于 `420-432` 判断无合并/无选中合并并返回。无匹配输入也付出了这部分成本。

将同一合成样本的 mergeCells 移除后，现路径中位 **0.701 秒**。一个仅流式检查首个顶层 mergeCells 的 scratch Expat 预检，在无匹配时直接返回，中位 **0.0599 秒（约少 91.5%）**，输出/count 与基线相同。但匹配样本增加一遍扫描后，**1.729 → 1.793 秒（约慢 3.68%）**；真实 ZIP 中还可能增加一次解压，当前 bytes 输入测试没有计入这部分。

因此不建议现在对所有文件无条件增加预检。只有后续确认用户经常把已处理/没有合并的文件重复交给工具，才值得研究这个切口。必须保留无匹配原样、无需生成新文件的行为，不扩大坐标/元数据拒绝范围；还要验证损坏 XML、外部实体和 ZipExtFile 重新定位的兼容性。可通过局部开关回退到当前单次首遍扫描，验收必须同时比较匹配与无匹配负载，防止为少数场景拖慢主要业务。

## 未推荐合入的微优化

| Scratch 变体 | 无 profiler 中位秒数 | 相对同轮基线 | 结论 |
| --- | ---: | ---: | --- |
| 单行 StringIO 改 list/join | 1.728 | 慢 0.05% | 无收益，保留当前缓冲 |
| 缓存不可变锚点的 namespace/xml:space 上下文 | 1.710 | 快 0.97% | 收益小于应优先处理的工程成本 |
| 第二遍只解码已验证地址的列号 | 1.694 | 快 1.89% | 收益小，需维护两套坐标逻辑 |
| 复用 ExpatBuilderNS 实例 | 1.719 | 快 0.43% | 构造器复用没有解决每行重解析 |
| serializer 先 hasAttributes，跳过空 NamedNodeMap | 1.677 | 快 3.05%（另一轮基线 1.729） | 可作以后局部整理，不足以声称显著缩短月表 |

上述否定性结果同样保留，避免从 profiler 中看到热点就承诺改一行会大幅加速。现阶段保留已验收的流式实现，优先完善处理阶段/耗时/预计等待反馈，比为这些微小差异再次承担整套保真回归更合理。

复现入口为同目录 `profile_stream.py`、`probe_candidates.py`、`probe_paths.py`；输出路径默认拒绝覆盖，可通过 `--report` 指向新的 JSON。本审查没有提交或发布修改。
